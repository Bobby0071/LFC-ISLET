# LFC-ISLET 项目说明（供外部审核）

> 版本 1.0.0 · 分支 `main` · 基于 fly-island v3.2.5（上游提交 `cf3ce21`）
> 本文档自洽，不需要额外背景即可阅读。涉及许可证的表述不构成法律意见。

## 一、项目定位与背景

### 这是什么

LFC-ISLET 是一款 Windows 优先的桌面"灵动岛"工具：常驻屏幕顶部的一条悬浮岛，需要时展开、用完收起，把分散在多个窗口的高频操作集中到一处。

功能包括：微信/QQ/邮箱消息卡片、AI Agent（Claude Code / Codex / DSH / WorkBuddy 等）会话状态与审批、同步歌词与音乐控制、待办、剪贴板历史、文件中转、快捷翻译、插件系统。

技术栈：Tauri 2 + React 19 + TypeScript + Rust，仅在 Windows 上运行。

### 基于什么改造

本分支从上游 fly-island v3.2.5 分出，上游核心功能**一行未重写**，我们在其之上做增量改造。许可证为 GPL-3.0，衍生关系在 README 与关于页均有明确标注。

截至本文档，相对上游共 **15 个提交**。

### 项目性质（阅读全文的前提）

这是一个**个人爱好项目**，不是商业产品或团队项目：

- 维护者基本上只有作者本人，唯一的分发对象是亲友；
- 不追求用户规模，不设商业化目标，不承诺 issue 响应时效或长期维护；
- 开源的主要目的是**代码公开可见、便于分享**，而非建立社区。

因此本文档中出现的工程规范（测试、CI、文档）应理解为"作者让自己日后还能看懂、改得动"的投入，**不是对外的质量承诺**。审核意见也请按这个尺度给出——不必按商业项目的标准评判。

### 目标

1. 让岛本身更"自足"——减少为了看一条信息而切换窗口；
2. 修正上游在浅色主题下的可读性问题；
3. 建立独立的版本线与发布节奏，不再跟随上游更新通道；
4. 保证作者本人半年后回来仍能读懂、敢改。

## 二、关键决策及其理由

### 决策 1：版本号定为 1.0.0

**决定了什么**：把三处版本号（`package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`）从继承来的 `3.2.5` 改为 `1.0.0`。

**为什么**：继续沿用 3.2.x 会让下载者误以为是上游的小版本更新。1.0.0 表明这是一个功能完整的独立发行版，与上游版本线彻底分离。代价是放弃"版本号延续性"这一层暗示。

### 决策 2：保持应用内自动更新通道关闭

**决定了什么**：`tauri.conf.json` 中 `updater.endpoints` 为空数组、`pubkey` 为空字符串，README 明确写明"本分支不提供自动更新"。

**为什么**：启用 Tauri 自动更新需要一套签名密钥、公开的 release 分发点和 `latest.json`，任何一环维护不到位，用户会卡在一个无法自更新的版本上。与其配置一个半途而废的通道，不如明确关闭并写清楚，让用户知道要手动拉取源码重建。

### 决策 3：保留上游的历史引用，不做清理

**决定了什么**：`docs/reviews/`、`docs/releases/v0.2.x.md` 等历史文档中提到上游作者与项目名的内容保留原样。

**为什么**：这些是开发过程记录，删除会破坏可追溯性，也不符合 GPL-3.0 对来源标注的要求。同时**关于页的社群群号、Star 引导、打赏入口已移除**（这些是当前生效的推广入口，与历史记录性质不同），只保留许可证要求的归属声明。

### 决策 4：品牌与标识独立

**决定了什么**：改名 LFC-ISLET，应用标识改为 `com.lfcislet.island`，断开上游更新通道，并提供旧数据自动迁移。

**为什么**：上游标识意味着共享数据目录与更新通道，两者都会导致"本分支被上游发布覆盖"或"配置文件互相污染"。分开后两边可独立演进。代价是**今后从上游同步会持续产生冲突**，这一点在下文待决事项中列出。

## 五、待决事项

### A. 远程仓库：GitHub，公开（已定，待执行）

**决定**：托管在 GitHub，仓库公开。

**剩余动作**：仓库尚未创建，因此 `git remote origin` 仍指向上游仓库 `github.com/flyl1u/fly-island`。**这是当前唯一未完成的阻塞项**——在重指向之前，任何人 clone 后执行 `git push` 都会推向上游仓库。

**执行步骤**：在 GitHub 建一个空仓库（不勾选 README / .gitignore），执行 `git remote set-url origin <新地址>` 后推送。本机未安装 GitHub CLI，此步需人工完成。

### B. 应用内自动更新：保持关闭，由用户自行选择是否更新（已定）

**决定**：不启用 Tauri 自动更新通道（`endpoints` 与 `pubkey` 保持为空），README 明确说明需手动更新。

**为什么**：这是一个个人维护的项目，没有持续的发版与分发运维投入。配一个长期无人维护的更新通道，比明确关闭更容易让用户卡住。用户如需更新，从仓库拉取源码重新构建即可，这是可预期且可控的方式。

### C. 是否向上游回馈改动：不做（已定）

**决定**：不向上游提交 issue 或 PR。

**为什么**：本项目定位为个人爱好（见上文"项目性质"），维护者无意参与上游的协作流程。且本分支的改动包含品牌改名与推广入口删减，本身也不适合作为上游 PR 的内容。上游若自行发现并修复浅色主题的对比度问题，属于其独立演进，与本分支无关。

**遗留影响**：这意味着本分支与上游是两条独立的线，今后不再合并上游改动。相关风险见第六节。

## 六、已知未处理项与风险

### 未处理项

| 项目 | 为什么没做 |
|---|---|
| **干净机器验证发布产物** | 当前只在开发机验证过 release 构建能启动。系统页依赖 Win32 性能计数器、通知依赖 WinRT，理论上都是系统自带，但未在无开发环境的机器上实测。**这是发布前建议补上的一项** |
| **新功能的回归测试** | 系统页与音量目前只有 Rust 单元测试，没有 `tests/regression/` 下的视觉/交互场景。补测试需要设计断言目标（哪些像素、什么交互状态），属于独立工作量 |
| **逐文件版权头核查** | 未逐文件检查源文件头的版权声明完整性。根目录 `LICENSE` 与 README 的归属说明是完整的，但源码层面未核实 |
| **上游同步策略** | 已断开更新通道，但**没有制定后续从上游合并的流程**。每次上游发版后如何 cherry-pick，目前无文档 |

### 风险

1. **上游同步成本会持续上升**：品牌、标识、主题色都改过，每次从上游合并都需要处理冲突。如果上游活跃，这部分成本会累积。
2. **1 个 Rust 测试长期失败**：`plugin_host::tests::built_artifacts_index_installs_and_runs` 依赖外网，在受限网络下失败。当前文档已说明，但会持续让 `cargo test --lib` 显示非零退出码，容易误判。
3. **单人维护**：目前无第二位维护者，issue 响应与发版节奏依赖单一时间投入。
4. **GPL-3.0 义务**：分发修改版须提供完整对应源码。若将来打包分发，需确认发布的源码与二进制一致。

## 七、希望审核方重点回答的问题

1. **方向性判断**：以上 12 项改动是否足以支撑"1.0.0 独立发行版"的定位？还是说当前更像是"0.x 早期分支"，应先积累用户反馈再谈 1.0？

2. **风险遗漏**：我们已决定不再向上游回馈、也不再合并上游改动（待决 C），这意味着上游的新功能与安全修复今后都需要手工移植。对于一个个人项目，这个决定是否合理？有没有低成本保持跟上上游的做法是我们没想到的？

3. **发布前必做项**：我们判断"干净机器验证发布产物"是发布前最该补的一项，其次是新功能回归测试。你认为这个优先级对吗？有没有被我们忽略的更高优先级项（例如安装器签名、崩溃上报、隐私说明）？

4. **优先级建议**：目前唯一未完成的是"把 git remote 指到自己的 GitHub 仓库"（待决 A），其余待决项均已定案。在正式推送之前，你是否认为还有别的必须先处理的事？

5. **个人项目定位下的取舍**：维护者把本项目定位为个人爱好，主要自用并分享给亲友，不追求用户规模、不设贡献门槛、不承诺响应时效。在这个前提下，你认为当前这套工程规范（419 项测试、完整 CI、81 篇文档、贡献指南与 issue 模板）是否**投入过度**？还是说这些投入对"自己日后还能看懂、改得动"是合理的？这是我们最想听到坦率意见的一点。
